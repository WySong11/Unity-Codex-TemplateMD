# Unity 빌드 및 검증 규칙

이 문서는 Unity 프로젝트의 빌드 준비, 실행, 산출물 확인 및 실패 처리 기준을 정의한다. 실제 빌드 수행, 빌드 설정 변경과 빌드 오류 분석 작업에 적용한다.

> 빌드 문서 작성·검토 요청 자체는 빌드 실행이나 배포 지시가 아니다. 사용자 요청과 `AGENTS.md`를 우선하며, 파일 저장·이력·Git 처리는 각각 `FILE.md`, `HISTORY.md`, `GIT.md`를 따른다.

---

## 1. 작업 범위와 완료 기준

작업 시작 전에 다음 항목을 구분한다.

| 작업 | 확인할 결과 |
|---|---|
| 빌드 방법 안내 | 현재 환경에 맞는 절차와 필요한 설정 |
| 빌드 설정 변경 | 요청한 설정의 저장 결과와 영향 |
| 빌드 실행 | 빌드 성공 여부, 로그와 산출물 |
| 실행 검증 | 대상 환경에서의 시작·핵심 기능 동작 |
| 배포 | 지정한 채널의 업로드·게시 결과 |

빌드 성공, 실행 성공과 배포 성공은 각각 별도로 보고한다. 빌드 요청만으로 스토어 제출, 공개 업로드나 운영 서버 배포까지 수행하지 않는다.

---

## 2. 빌드 환경 확인

다음 항목을 프로젝트 파일, Editor와 기존 자동화에서 확인한다. 확인되지 않은 값은 추정하여 채우지 않는다.

| 항목 | 확인 내용 |
|---|---|
| 프로젝트 경로 | `Assets`, `Packages`, `ProjectSettings`가 있는 실제 루트 |
| Unity 버전 | `ProjectSettings/ProjectVersion.txt`와 실행할 Editor의 버전 |
| 패키지 | `manifest.json`, `packages-lock.json`과 복원 상태 |
| 대상 | 플랫폼, 아키텍처와 사용할 Build Profile 또는 기존 설정 |
| 실행 환경 | 필요한 플랫폼 모듈, SDK·NDK·JDK 등 도구와 라이선스 상태 |
| 빌드 방식 | Editor 수동 빌드, 기존 Editor 빌드 코드 또는 CI |
| 코드 상태 | 현재 브랜치·커밋과 빌드에 포함될 미커밋 변경 |
| 출력 위치 | 실제 절대 경로, 기존 산출물과의 충돌 여부 |

- 프로젝트에 지정된 Unity 버전을 사용하고 빌드를 위해 임의 업그레이드하지 않는다.
- 필요한 도구가 없으면 누락 항목을 특정하고 설치·변경이 요청 범위에 포함되는지 판단한다. CLI·MCP·Pipeline 준비의 범위와 점검 주기는 UNITY_TOOLING.md를 따른다. 빌드마다 전체 최신 조회를 반복하지 않는다.
- 사용자가 특정 커밋·고정 의존성의 재현 빌드를 지시했다면 그 지시를 우선한다. Pipeline 자동 업데이트로 빌드 입력을 바꾸지 말고, 필요한 경우 도구 업데이트를 보류한 이유를 보고한다.
- 플랫폼 전환과 패키지 복원에 따른 재임포트·설정 변경을 고려한다.
- 동일 프로젝트를 사용하는 Editor·빌드 작업을 중복 실행하지 않는다. 사용 중인 Editor를 임의로 종료하지 않는다.

## 3. 빌드 전 확인

1. 사용자 변경과 저장되지 않은 씬·프리팹 변경을 확인한다.
2. 패키지 복원, 임포트와 스크립트 컴파일 상태를 확인한다.
3. 새로운 Error·Exception과 빌드를 막는 기존 오류를 구분한다.
4. 빌드에 포함할 씬, 활성 여부와 시작 순서를 확인한다.
5. 해당 버전의 Build Settings 또는 Build Profiles와 씬 목록 Override 여부를 확인한다.
6. 필수 에셋, Inspector 참조 및 플랫폼별 플러그인 설정을 확인한다.
7. 개발·검증·운영 중 사용할 환경과 설정을 확인한다.
8. 이번 빌드의 성공 조건과 실행 검증 범위를 정한다.

오류를 숨기거나 Console을 지우는 것으로 문제를 해결했다고 판단하지 않는다. 설정 변경 없이 빌드가 가능한 경우 기존 설정을 유지한다.

## 4. 개발용·배포용 설정

- Development Build, Script Debugging과 Profiler 연결은 요청한 빌드 목적에 맞게 설정한다.
- 배포용 빌드에는 의도하지 않은 디버그 기능, 테스트 계정과 테스트 환경 연결이 남지 않도록 확인한다.
- Scripting Backend, API Compatibility Level, Managed Stripping Level, 그래픽 API와 아키텍처는 기존 프로젝트와 대상 환경을 기준으로 선택한다.
- IL2CPP, 리플렉션과 코드 스트리핑 관련 변경은 해당 기능이 실제 빌드에서도 동작하는지 확인한다.
- Bundle Identifier, 버전·빌드 번호와 서명 설정은 요청이나 정해진 배포 정책 없이 임의로 변경하지 않는다.
- 빌드 중 변경한 설정은 목록으로 남긴다. 임시 설정을 복구할 때는 이번 작업에서 바꾼 값만 원래 값으로 되돌린다.

## 5. 출력 경로와 산출물

- 빌드 산출물은 `Assets`, `Packages`, `ProjectSettings`와 분리한다.
- 기존 정책이 없다면 프로젝트의 `Builds/<Platform>/<BuildName>/` 같은 별도 폴더를 검토한다. 실제 경로는 실행 전에 확정한다.
- 실행 파일 하나만으로 완성된 결과라고 판단하지 않고 플랫폼이 요구하는 데이터·라이브러리·콘텐츠를 함께 확인한다.
- 이전 산출물을 보존할 필요가 있으면 새 출력 경로를 사용한다.
- 기존 폴더를 정리할 때는 절대 경로와 삭제 대상을 확인하며 사용자 데이터가 섞인 폴더를 재귀 삭제하지 않는다.
- 산출물·로그·디버그 심볼의 보관 및 Git 포함 여부는 기존 정책을 따른다. 일반 소스 변경에 자동으로 stage하지 않는다.

## 6. 빌드 실행

### Editor 빌드

1. 확인한 프로젝트와 Unity 버전을 연다.
2. 대상 플랫폼과 사용할 프로필·씬 목록을 확인한다.
3. 검증한 옵션과 출력 경로로 빌드를 실행한다.
4. 완료 결과, Build Report 또는 Editor 로그와 실제 산출물을 확인한다.

### 자동화·CI 빌드

- 기존 빌드 스크립트·CI 정의를 우선 사용한다.
- 실행 파일, 프로젝트 경로, 대상, 진입점과 인수를 실제 환경에서 확인한다.
- `-executeMethod`를 사용하는 경우 해당 Editor 빌드 메서드가 실제로 존재하고 호출 가능한지 확인한다.
- 새 빌드 코드를 만들면 Editor 전용으로 분리하고 빌드 실패가 프로세스·CI 실패로 전달되도록 한다.
- 콘솔 출력뿐 아니라 빌드 결과, 종료 코드와 산출물의 생성 시각을 함께 확인한다.
- 비밀 값을 명령줄·로그에 노출하지 않고 기존 보안 변수 또는 비밀 관리 방식을 사용한다.
- 성공·실패 시 모두 원인을 조사할 수 있는 로그를 보관한다.

### Unity CLI beta.16의 실행 중 Editor 빌드 (지원 구성에 한함)

- Unity CLI `1.0.0-beta.16` 이상은 `unity build --target`을 **해당 프로젝트를 이미 열어둔 Unity Editor로 수행**할 수 있다. 반드시 설치된 CLI와 연결된 Editor의 지원 여부·호환성을 확인하고, 실행 전 `unity build --help`로 실제 타깃·옵션을 확인한다.
- 열린 Editor를 사용할 경우 **활성 빌드 타깃이 변경될 수 있다.** 프로젝트의 저장되지 않은 씬·설정·사용자 변경을 보호하고, 대상 플랫폼 전환 및 재임포트 영향을 미리 검토한다.
- Editor가 Play Mode, 스크립트 컴파일 중이거나 모달 팝업을 기다릴 때에는 열린 Editor 빌드가 거부될 수 있다. 연결 상태 및 `UNITY_TOOLING.md` 7.1절의 오류 분류를 먼저 확인한다.
- `--execute-method`, `--profile`, `--args`, `--accelerator`/`--no-accelerator`, `--log-file`, `--editor-path`, 열린 Editor와 다른 `--editor-version`, `--architecture`, `--build-target-group`, `--android-*` 등 **별도 Editor 프로세스가 필요한 옵션**을 사용하는 경우에는 열린 Editor 방식으로 강행하지 않는다. 공식 CLI 도움말과 기존 CI 방법을 따른다.
- `--timeout`이나 Ctrl+C는 **CLI가 빌드를 기다리는 동작만 중단**할 수 있다. 이미 열린 Editor에서 시작된 빌드는 계속 실행될 수 있으므로, 종료 코드나 대기 중단만으로 빌드의 성공·실패·취소를 단정하지 않는다.
- 빌드 완료 판정은 Editor의 실제 완료 상태·Build Report·산출물을 기준으로 하며, 사용 중인 Editor를 임의 종료하지 않는다. 열린 Editor 빌드가 불가능하면 자동으로 Editor를 종료하지 않고 별도 빌드 경로의 허용 여부를 확인한다.

```powershell
# 지원되는 빌드 대상과 옵션을 우선 확인
unity build --help
# 실제 대상·프로젝트 경로를 확인한 뒤 실행 (임의로 타깃 값을 가정하지 않음)
# unity build --target <확인된-빌드-타깃> --project-path "$UnityProjectRoot"
```

존재하지 않는 빌드 진입점이나 확인하지 않은 명령을 실행 가능한 프로젝트 명령처럼 제시하지 않는다. 구체적인 명령을 추가할 때는 설치된 Unity·CLI 버전의 공식 사용법을 확인한다.

## 7. Addressables와 외부 콘텐츠

해당 기능을 사용하는 프로젝트에만 적용한다.

- Player 빌드와 콘텐츠 빌드의 기존 선후 관계 및 자동 빌드 설정을 확인한다.
- 사용할 Addressables Profile, 로컬·원격 경로와 카탈로그를 확인한다.
- 콘텐츠 업데이트 작업에서는 기존 릴리스와 필요한 상태 파일을 보존한다.
- Player와 콘텐츠의 호환성, 원격 콘텐츠 접근 및 첫 실행 다운로드를 검증한다.
- 콘텐츠가 만들어졌다는 사실과 서버에 업로드되었다는 사실을 구분한다.
- 원격 경로 변경이나 콘텐츠 게시가 요청 범위에 포함되지 않으면 임의로 수행하지 않는다.

## 8. 플랫폼별 추가 확인

아래 표는 확인 항목이며, 프로젝트에 적용되는 SDK 버전·정책·설정값은 현재 설치 환경과 해당 플랫폼의 공식 문서에서 확인한다.

| 대상 | 추가 확인 사항 |
|---|---|
| Windows·macOS·Linux | 아키텍처, 네이티브 플러그인, 실행 권한, 파일 경로와 필수 동봉 파일 |
| Android | SDK·NDK·JDK, 패키지 형식, 식별자, ABI, 서명과 실기기 설치 |
| iOS | 지원되는 macOS·Xcode 환경, 생성된 Xcode 프로젝트, 서명·프로비저닝과 실기기 검증 |
| Web | 적절한 HTTP 서버, 압축·응답 헤더, HTTPS 요구, 브라우저·메모리·네트워크 동작 |
| 전용 서버 | 서버 대상과 런타임 의존성, 시작 옵션, 포트·접속 및 종료 동작 |

iOS 프로젝트 생성은 서명된 앱 생성과 구분한다. Web 산출물은 파일을 직접 여는 방식만으로 실행 검증을 마쳤다고 판단하지 않는다.

## 9. 테스트와 실행 검증

변경 위험과 사용자 요청에 맞는 검증을 선택한다. 단순 문서 변경만으로 전체 Player 빌드를 의무화하지 않는다.

- 관련 Edit Mode·Play Mode 테스트가 있으면 변경 범위에 맞게 실행한다.
- Unity CLI beta.17 이상에서 `unity test`로 NUnit·JUnit 보고서를 함께 출력할 때는 각각의 결과 파일을 구분해 존재 여부·완료 시각·테스트 수·실패 수를 확인한다. 두 보고서가 하나의 파일로 덮어써지지 않았는지 검사한다.
- Unity MCP의 비동기 테스트 요청은 **요청 접수·대기·실제 완료·최종 통과**를 구분한다. beta.17의 완료 대기 개선이 있더라도 실행 중 상태나 생성되지 않은 리포트를 성공으로 판정하지 않는다.
- 실제 산출물을 대상 환경에서 실행해 시작 씬과 초기화를 확인한다.
- 입력, UI·한글 표시, 오디오와 씬 전환 등 변경된 기능을 확인한다.
- 네트워크 기능 변경 시 접속·실패·재접속 및 환경별 설정을 확인한다.
- 저장 경로, 권한, 에셋 로딩과 플랫폼 전용 코드가 필요한 환경에서 동작하는지 확인한다.
- 성능 최적화 작업이면 실제 대상 환경에서 관련 지표를 측정한다.

Editor Play Mode 성공을 Player 실행 성공으로 대체하지 않는다. 장치나 플랫폼 환경이 없으면 빌드 검증과 실행 미검증 상태를 따로 기록한다.

### 9.1 UI Toolkit 화면·코드·에셋 변경 시 추가 확인

UI Toolkit 변경 작업에는 아래 항목 중 **실제로 영향을 받는 범위**를 확인한다. `AGENTS.md` 5절, `UNITY_CS_CODING_RULES.md` 20절 및 `UNITY_ASSET_RULES.md` 4.1절의 규칙을 함께 적용한다. 해당 UI를 변경하지 않은 빌드 작업이나 문서 수정만으로 모든 UI 검사 또는 전체 Player 빌드를 강제하지 않는다.

| 검증 대상 | 확인 내용 |
|---|---|
| `UIDocument` | Source Asset(UXML), Panel Settings 및 필요한 정렬·표시 연결이 유효한지 확인 |
| UXML | 화면 요소 생성·조회(`rootVisualElement`, 요소 `name`)와 템플릿·스타일 참조 확인 |
| USS | 스타일시트 로딩, 선택자·클래스, 동적 클래스 적용 및 Theme Style Sheet 영향 확인 |
| 한글·폰트 | 한글 글리프, fallback, 특수문자·줄바꿈·동적 문자열의 표시 확인 |
| 화면 해상도 | 기준 해상도·스케일·가로세로 비율·안전 영역에 따른 레이아웃 확인 |
| 입력·포커스 | 마우스·키보드·게임패드·터치 중 대상 플랫폼에 해당하는 입력과 포커스·이벤트 확인 |
| 생명주기 | `OnEnable`/`OnDisable`, 이벤트 등록·해제, 재활성화 시 중복 이벤트 발생 여부 확인 |
| 씬 전환 | 화면 초기화·해제·재진입, PanelSettings 공유 및 UI 잔존 여부 확인 |

- 검증 수준은 **정적 검사/컴파일 → Editor Play Mode → 실제 Player** 중 작업 위험과 사용자가 요청한 완료 기준에 따라 선택한다. 각 수준을 독립적으로 판정하고, 수행하지 않은 단계는 `미검증`으로 표시한다.
- 대상 플랫폼에서만 발생 가능한 폰트·해상도·터치 등의 문제를 해결했다고 주장하려면 가능하면 해당 플랫폼의 **실제 Player**에서 검증한다. 장치나 빌드 환경이 없다면 Editor 검증과 Player 미검증을 구분한다.
- Unity Editor·패키지 버전에 없는 API 또는 Inspector 옵션을 있다고 가정하지 않고 현재 설치 환경을 확인한다.

### 9.2 Assembly Definition(.asmdef·.asmref) 변경 시 검증

- 실제 어셈블리 구성을 수정한 경우 [UNITY_ASSEMBLY_RULES.md](UNITY_ASSEMBLY_RULES.md)에 따라 Unity 재컴파일 완료 및 Console 최초 오류를 확인한다. 누락 참조, `Assembly-CSharp` 참조 제한, 순환 참조, Editor 전용 API 유입을 점검한다.
- 관련 EditMode·PlayMode 테스트 어셈블리 참조와 테스트 결과, 씬·프리팹·ScriptableObject 직렬화/Inspector 연결을 확인한다.
- 요청과 영향 범위에 맞는 Player 빌드만 검증하고 실제 실행하지 못한 단계는 `미검증`으로 보고한다. 문서 수정만으로 전체 빌드를 실행하지 않는다.

## 10. 실패 처리

1. 실패 단계를 환경 준비·임포트·컴파일·콘텐츠 빌드·Player 빌드·실행·배포로 구분한다.
2. 최초 원인 오류와 뒤따르는 오류를 구분하고 핵심 로그를 보존한다.
3. 로그와 설정을 근거로 필요한 최소 수정만 수행한다.
4. 원인이 해결된 후 필요한 단계만 다시 실행한다.
5. 실패한 출력과 이전 성공 산출물이 혼동되지 않도록 실제 경로와 시각을 기록한다.

`Library` 삭제, 전체 재임포트, 패키지·Unity 업그레이드를 근거 없는 기본 해결책으로 사용하지 않는다. 부분 산출물이나 오래된 실행 파일을 이번 빌드의 성공 결과로 보고하지 않는다.

## 11. 결과 기록과 보고

빌드 결과에는 다음 항목 중 해당 사항을 포함한다.

```text
작업 범위: 설정 변경 / 빌드 / 실행 검증 / 배포
Unity 버전:
플랫폼·아키텍처·프로필:
소스 상태: 커밋 ID 및 미커밋 변경 포함 여부
빌드 옵션과 환경:
변경한 설정:
빌드 시작·종료 시각 및 시간대:
빌드 결과: 성공 / 실패 / 미실행
산출물 경로:
로그 경로:
실행 검증: 성공 / 실패 / 미실행 및 이유
배포 결과: 성공 / 실패 / 미실행 / 해당 없음
남은 문제와 후속 조치:
```

작업 이력 생성 여부와 형식은 `HISTORY.md`를 따른다. 로그·산출물 생성과 프로젝트 소스·설정 변경을 구분하고, 기록 대상 여부가 불명확하면 실제 변경 목록을 기준으로 판단한다. Git 전달은 `GIT.md` 조건을 별도로 확인한다.
