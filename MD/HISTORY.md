# 작업 이력 기록 규칙

이 문서는 AI 에이전트가 프로젝트 작업 이력을 일관된 형식으로 생성하고 관리하기 위한 필수 규칙이다.

AI 에이전트는 기록 대상 작업의 지시 내용, 수행 과정, 변경 사항 및 결과를 HTML 형식으로 기록한다. 기록 대상 여부는 아래 적용 범위에 따라 작업 이력 파일 생성 전에 판단한다.

> 작업 코드나 에셋 변경이 끝났더라도 작업별 상세 기록과 `History/History.html` 갱신이 누락되면 해당 작업은 완전히 완료된 것으로 간주하지 않는다.

---

## 1. 적용 범위

- 작업 이력 파일을 제외한 프로젝트 파일을 실제로 생성·수정·삭제한 작업에 대해 이력을 생성한다.
- 실제 프로젝트에 반영하는 코드, 에셋, 설정, 문서 변경을 포함한다. 첨부 문서의 수정본만 전달하는 작업은 프로젝트 반영과 구분하며, 실제 프로젝트 루트 없이 History 폴더를 임의 생성하지 않는다.
- 캐시, 임시 파일, 빌드 산출물·로그만 생성된 경우에는 기본적으로 소스·설정 변경으로 간주하지 않는다. 결과는 응답으로 보고하고, 별도 이력 요청이나 기존 산출물 관리 정책이 있을 때 해당 범위만 기록한다.
- 사용자 전역 CLI·MCP 설정만 바뀐 경우도 프로젝트 변경 이력을 자동 생성하지 않는다. 프로젝트 로컬 설정이나 Pipeline 의존성 변경은 기록 대상이다.
- 실패·부분 완료 작업도 실제 파일 변경이 발생했다면 기록한다. 이후 변경을 복구한 경우에는 복구 사실을 기록한다.
- 파일 변경이 없는 분석·설명·점검은 HTML과 인덱스를 생성하거나 수정하지 않는다. 사용자가 이력 작성 자체를 명시적으로 요청한 경우는 예외이며, 기록 생성만으로 자동 commit/push 대상으로 확대하지 않는다.
- 하나의 사용자 지시에 서로 관련된 여러 요구사항이 포함된 경우 하나의 작업 기록으로 관리할 수 있다.
- 같은 진행 중 작업에 대한 보충·정정은 같은 기록에 반영한다. 완료된 작업 이후 별개의 파일 변경 작업을 요청하면 새 기록을 생성한다.
- 하나의 작업에 대한 기록 파일 작성과 인덱스 갱신은 같은 작업의 마무리 단계로 처리한다. 기록 파일을 생성했다는 이유만으로 기록용 작업을 다시 재귀적으로 생성하지 않는다.

---

## 2. History 폴더

모든 작업 이력은 프로젝트 루트의 `History` 폴더에서 관리한다.

```text
<ProjectRoot>/
└── History/
```

- `History` 폴더가 없다면 첫 작업 기록 시 자동으로 생성한다.
- 프로젝트 루트를 먼저 정확히 확인한 뒤 폴더를 생성한다.
- Unity 프로젝트에서는 일반적으로 `Assets`, `Packages`, `ProjectSettings` 폴더가 있는 위치를 프로젝트 루트로 판단한다.
- 프로젝트 루트를 확정할 수 없다면 임의의 위치에 만들지 말고 사용자에게 확인한다.
- 기존 `History` 폴더와 기록 파일을 보존한다.

## 3. 작업별 개별 HTML 파일

각 작업 지시는 하나의 독립된 HTML 파일로 기록한다.

- 여러 작업의 상세 내용을 하나의 파일에 계속 덧붙이지 않는다.
- 기록 대상인 별개의 작업마다 새로운 HTML 파일을 생성한다.
- 기존 상세 기록 파일을 새 작업 내용으로 덮어쓰지 않는다.

### 3.1 파일 이름 형식

다음 형식을 사용한다.

```text
YYYY-MM-DD_HH-mm_간략한-작업명.html
```

예시:

```text
2026-07-06_15-30_AGENTS-규칙-추가.html
2026-07-06_16-10_캐릭터-이동-오류-수정.html
2026-07-06_17-20_UI-패널-생성.html
```

### 3.2 파일 이름 작성 규칙

- 기본 시간대는 Asia/Seoul(UTC+09:00)이며 사용자가 지정한 시간대가 있으면 이를 따른다. HTML에도 시간대를 표기한다.
- 작업 지시 시각을 확인할 수 있으면 해당 시각을 사용한다. 확인할 수 없으면 파일명에는 실제 기록 생성 시각을 사용하고 본문에는 작업 지시 시각 확인 불가와 기록 생성 시각을 구분하여 적는다. 현재 시각을 과거 지시 시각으로 단정하지 않는다.
- 작업명은 작업의 핵심 내용을 알아볼 수 있도록 짧고 구체적으로 작성한다.
- 공백은 하이픈(`-`)으로 바꾸는 것을 권장한다.
- 작업명이 너무 길면 핵심 의미가 유지되는 범위에서 줄인다.
- Windows 파일 이름에서 사용할 수 없는 다음 문자는 사용하지 않는다.

```text
\ / : * ? " < > |
```

- 같은 분에 같은 이름의 기록이 이미 있으면 기존 파일을 덮어쓰지 않는다.
- 파일명이 충돌하면 초 또는 순번을 추가한다.

```text
YYYY-MM-DD_HH-mm-ss_간략한-작업명.html
YYYY-MM-DD_HH-mm_간략한-작업명_02.html
```

## 4. 개별 작업 기록에 포함할 내용

각 작업별 HTML 파일에는 다음 항목을 반드시 기록한다.

### 4.1 기본 정보

- 작업 지시 시간
- 작업 완료 시간
- 작업 제목
- 작업 상태

작업 상태는 다음 중 하나를 사용한다.

| 상태 | 기준 |
|---|---|
| 완료 | 요청한 범위의 작업과 검증 및 기록을 완료함 |
| 부분 완료 | 일부는 완료했으나 남은 작업이 있음 |
| 실패 | 핵심 목표를 달성하지 못함 |
| 사용자 확인 필요 | 기술적으로 진행했으나 선택, 권한, Unity Editor 확인 등이 필요함 |

### 4.2 사용자 지시

- 사용자가 요청한 원래 작업 내용
- 작업의 핵심 목표
- 사용자가 지정한 조건과 제한 사항

사용자의 원래 지시는 의미가 바뀌지 않도록 기록한다. 지나치게 긴 첨부 자료나 로그는 전체를 복사하지 않고 요청의 핵심과 참조 파일을 정리한다.

### 4.3 작업 판단 및 수행 과정

- 작업 전에 확인한 프로젝트 구조
- 확인한 관련 파일과 기존 구현
- 선택한 구현 방식
- 해당 방식을 선택한 이유
- 실제로 수행한 주요 단계
- 작업 중 발견한 문제
- 문제의 원인과 해결 방법
- 적용한 Skill, 프로젝트 규칙 또는 기술 기준

AI의 비공개 내부 사고 전체를 기록하지 않는다. 대신 사용자가 결과를 검토하고 재현할 수 있도록 판단 근거와 작업 과정을 명확하고 구체적으로 요약한다.

### 4.4 파일 변경 내역

작업으로 인해 생성, 수정, 삭제 또는 확인된 파일을 구분하여 기록한다.

- 생성한 파일
- 수정한 파일
- 삭제한 파일
- 확인만 하고 변경하지 않은 파일

각 파일에 대해 다음 내용을 함께 기록한다.

- 파일 경로
- 수행한 작업
- 변경 이유
- 주요 변경 내용

파일 변경이 없었다면 다음과 같이 명시한다.

```text
파일 변경 없음
```

작업 기록 파일 자체도 해당 작업에서 생성·수정한 파일 목록에 포함한다.

예시:

```text
생성:
- History/2026-07-06_15-30_AGENTS-규칙-추가.html
  - 작업 상세 기록 생성

수정:
- AGENTS.md
  - 작업 이력 기록 규칙 추가
- History/History.html
  - 최신 작업 인덱스 항목 추가

삭제:
- 없음

확인만 수행:
- UNITY_CS_CODING_RULES.md
  - C# 규칙과 충돌 여부 확인, 변경 없음
```

### 4.5 작업 결과

- 최종 구현 내용
- 해결된 문제
- 아직 해결되지 않은 문제
- Unity Inspector에서 필요한 추가 설정
- 사용자가 직접 확인해야 하는 사항
- 후속 작업이 필요한 경우 그 내용

### 4.6 Git 상태의 기록 시점과 최종 결과 분리

작업 이력 HTML은 **commit 전에 생성한 작업 스냅샷**으로 관리하고, commit/push **이후의 최종 전달 결과**는 Git 로그와 Codex의 사용자 최종 보고에서 확인한다. 구현 완료와 원격 반영 완료를 혼동하지 않는다.

| 정보 | 기준 기록 위치 |
|---|---|
| 사용자 지시·작업 내용·변경 파일·검증 결과 | 작업별 상세 HTML 및 `History.html` 요약 |
| HTML 작성 당시의 Git 처리 상태 | 작업별 상세 HTML: `Commit/Push: 미실행 (기록 작성 시점)` 또는 이미 확정된 사전 미수행 사유 |
| commit 성공 여부·최종 commit ID | 실제 Git 로그 및 사용자 최종 보고 |
| push 성공·실패·미수행·확인 불가, 대상 원격·브랜치 | 사용자 최종 보고(실제 명령 결과에 근거) |
| 후속 Git 처리 실패와 남은 로컬 변경 | 사용자 최종 보고; 별도 요청 시에만 기존 HTML 보완 |

- 아직 시도하지 않은 commit/push 결과를 HTML에 성공이나 실패로 예상해서 쓰지 않는다. 사전 안전 검사에서 작업 중지가 확정되었다면 **commit 전에** 미수행 이유를 실제 상태대로 기록할 수 있다.
- commit 이후에는 성공·실패·안전 조건 미충족 여부를 이유로 작업별 HTML이나 `History.html`을 **자동 수정하지 않는다.** 특히 최종 commit ID와 push 성공을 같은 commit에 포함시키려고 반복 commit하거나 amend하지 않는다.
- 사용자가 **명시적으로** 같은 작업의 Git 후속 결과를 HTML에 보완하라고 요청한 경우에만, 기존 기록을 보존한 채 시각·근거·Git 결과를 추가하고 필요 시 인덱스 요약을 갱신한다. 이는 새로운 작업 기록을 재귀적으로 생성하지 않으며, 기록 보완만을 이유로 자동 commit/push하지 않는다. 보완으로 남은 미커밋 파일을 최종 보고한다.
- Git 처리 중단·오류 및 후속 조치는 `GIT.md` 13절을 따른다. 미수행과 실행 실패, 그리고 결과 확인 불가를 구분한다.

### 4.7 테스트 및 검증

- 수행한 테스트 방법
- 테스트 결과
- 수행하지 못한 테스트와 그 이유
- 사용자가 직접 확인할 수 있는 테스트 절차

Unity Editor를 실제로 실행하지 못했다면 컴파일, Play Mode, Inspector 또는 빌드 검증을 완료했다고 단정하지 않는다.

## 5. 전체 이력 관리 파일

`History` 폴더에는 전체 작업 기록을 관리하는 다음 파일을 유지한다.

```text
History/History.html
```

`History.html`은 모든 상세 내용을 반복해서 담는 파일이 아니라, 전체 작업 이력을 빠르게 확인하기 위한 인덱스 파일이다.

기록 대상 작업을 처리할 때 다음 순서를 지킨다.

1. 작업별 개별 HTML 파일을 생성한다.
2. 생성한 개별 기록 파일을 확인한다.
3. `History.html`에 해당 작업의 요약과 링크를 추가한다.
4. 가장 최근 작업이 위에 표시되는지 확인한다.

`History.html`이 없다면 첫 기록을 생성할 때 함께 만든다.

## 6. History.html 필수 내용

`History.html`에는 각 작업에 대해 다음 정보를 기록한다.

- 작업 지시 시간
- 작업 제목
- 작업 상태
- 작업 내용 요약
- 생성한 파일
- 수정한 파일
- 삭제한 파일
- 개별 작업 기록 HTML 파일 링크

예시:

```text
2026-07-06 15:30
작업: AGENTS.md 작업 이력 규칙 추가
상태: 완료
요약: 프로젝트 작업 이력 기록 규칙과 HTML 기록 절차를 추가함
생성 파일:
- History/2026-07-06_15-30_AGENTS-규칙-추가.html
수정 파일:
- AGENTS.md
- History/History.html
삭제 파일:
- 없음
상세 기록: 2026-07-06_15-30_AGENTS-규칙-추가.html
```

### 6.1 정렬 및 링크 규칙

- 가장 최근 작업을 목록의 맨 위에 배치한다.
- 각 상세 기록으로 이동할 수 있는 상대 경로 링크를 사용한다.
- 링크 대상 파일이 실제로 존재하는지 확인한다.
- 과거 항목의 링크와 내용을 임의로 변경하지 않는다.

```html
<a href="2026-07-06_15-30_AGENTS-규칙-추가.html">
  상세 기록 보기
</a>
```

## 7. 상세 기록과 전체 인덱스의 역할

### History.html

- 전체 작업 목록과 요약을 관리한다.
- 최근 작업과 상태를 빠르게 확인할 수 있게 한다.
- 각 작업의 상세 HTML 파일로 이동할 수 있는 링크를 제공한다.

### 작업별 개별 HTML 파일

- 해당 작업의 사용자 지시를 기록한다.
- 판단 근거와 수행 과정을 상세히 기록한다.
- 생성, 수정, 삭제 및 확인한 파일을 기록한다.
- 작업 결과와 테스트 내용을 기록한다.

동일한 상세 내용을 `History.html`에 그대로 반복하지 않는다. `History.html`에는 요약과 상세 기록 링크만 남긴다.

## 8. 실패하거나 중단된 작업

적용 범위에 해당하는 작업이 실패하거나 완료되지 않은 경우에도 기록을 생략하지 않는다. 실제 파일 변경이 발생하지 않은 실패·점검은 사용자 응답으로만 보고한다.

다음 내용을 반드시 기록한다.

- 실패하거나 중단된 이유
- 실제로 완료된 범위
- 생성, 수정 또는 삭제된 파일
- 변경 사항을 원래 상태로 복구했는지 여부
- 복구하지 못한 변경 사항
- 남아 있는 문제
- 다음 작업에서 필요한 조치
- 사용자 확인이나 권한이 필요한 사항

실패한 작업을 `완료`로 표시하지 않는다. 일부 결과가 남았다면 `부분 완료`, 사용자 선택이나 외부 확인이 필요하면 `사용자 확인 필요`로 표시한다. **작업 구현 실패와 작업 완료 후의 Git push 실패는 별개의 상태**이므로, push가 실패했다는 이유만으로 이미 검증된 구현 결과의 작업 상태를 소급해 실패로 바꾸지 않는다. Git 실패는 최종 보고에 별도로 표시하고, commit 후의 HTML 자동 수정은 4.6절에 따라 금지한다.

## 9. 기존 작업 기록

이 규칙이 추가되기 전에 수행한 주요 작업도 확인 가능한 범위에서 정리할 수 있다.

```text
History/
├── History.html
└── YYYY-MM-DD_HH-mm_기존-작업-정리.html
```

기존 작업을 정리할 때는 다음 원칙을 따른다.

- 대화 기록, Git 기록, 기존 문서 등 확인 가능한 근거만 사용한다.
- 정확한 작업 시간을 확인할 수 없으면 임의로 단정하지 않는다.
- 추정한 내용을 확정된 사실처럼 기록하지 않는다.
- 여러 과거 작업을 하나로 정리했다면 범위와 근거를 명시한다.

정확한 시간이 확인되지 않는 경우 다음과 같이 기록한다.

```text
작업 시간: 정확한 작업 시간 확인 불가
정리 근거: 대화 또는 Git 기록을 기준으로 정리
```

## 10. 기록 생성 시점과 작업 순서

기록 대상인 프로젝트 변경 작업은 다음 순서로 처리한다.

1. 사용자 지시 확인
2. 프로젝트 규칙과 작업 범위 확인
3. 실제 작업 수행
4. 변경 파일과 결과 검토
5. 테스트 및 검증 결과 정리
6. 작업별 개별 HTML 파일 생성(작성 시점의 Git 상태만 기록)
7. `History.html` 인덱스 갱신
8. 기록 파일과 링크 확인
9. **Git 저장소인 경우** `GIT.md`의 stage 범위·비밀정보·원격 상태 안전 조건에 따라 commit 및 push를 각각 판정하고 실행
10. commit ID는 Git 로그에서 확인하고 push 성공·실패·미수행·확인 불가를 구분
11. **commit 후 History HTML/인덱스를 자동 수정하지 않고**, 사용자에게 실제 작업 결과·기록 경로·Git 최종 상태 보고

코드 또는 에셋 작업이 완료되었더라도 작업별 기록과 `History.html` 갱신이 누락되면 작업이 완전히 끝난 것으로 간주하지 않는다. Git 저장소가 아닌 경우에는 Git 단계를 생략하고 그 사실을 보고한다. 기록만 요청받은 경우에는 `GIT.md`의 자동 처리 예외를 적용한다.

진행 도중 세션이 중단될 가능성이 높거나 작업 규모가 큰 경우, 완료된 범위를 잃지 않도록 중간 상태를 메모할 수 있다. 최종 기록에는 실제 완료 상태만 반영한다.

## 11. 기록 파일 안전 규칙

- 기존 작업 기록을 임의로 삭제하지 않는다.
- 완료된 과거 기록을 다른 작업 내용으로 덮어쓰지 않는다. commit/push 후속 결과는 **자동 반영하지 않으며**, 사용자로부터 명시적인 보완 요청을 받았을 때만 기존 본문을 보존한 채 시각·근거와 함께 추가할 수 있다. 보완 결과의 미커밋 여부는 보고한다.
- 같은 파일명이 존재하면 초 또는 순번을 추가하여 새 파일을 생성한다.
- 기록 내용은 실제 작업 결과와 일치해야 한다.
- 수행하지 않은 작업을 완료했다고 기록하지 않는다.
- 확인하지 못한 Unity Editor 결과를 확인 완료라고 단정하지 않는다.
- 비밀번호, API 키, 인증 토큰, 개인정보는 기록하지 않는다.
- 긴 로그 전체를 그대로 복사하지 않고 핵심 오류와 해결 내용을 요약한다.
- 사용자 소유의 기존 변경 사항을 AI가 수행한 변경으로 기록하지 않는다.
- 파일이 생성·수정·삭제되었는지 실제 상태를 확인한 후 기록한다.
- 기록용 HTML에 외부 스크립트나 추적 코드를 추가하지 않는다.
- 사용자 요청·코드·로그는 HTML 텍스트로 이스케이프한다. 텍스트의 &, <, >를 엔티티로 변환하고, 속성값에는 따옴표도 이스케이프한다. 코드 블록도 예외가 아니다.
- 링크는 생성한 기록 파일에 대한 상대 경로를 사용한다. 파일명에 포함된 URL 특수문자는 경로 구성 요소 단위로 인코딩하며, 임의의 HTML이나 실행 가능한 URL을 삽입하지 않는다.
- HTML에는 UTF-8 문자 인코딩을 지정하여 한글이 깨지지 않도록 한다.

## 12. 작업 상태 결정 기준

기록 상태는 다음 순서로 판단한다.

1. 요청한 핵심 결과를 만들지 못했다면 `실패`
2. 일부만 구현되었거나 해결되지 않은 문제가 남았다면 `부분 완료`
3. 구현은 끝났지만 사용자 선택, Inspector 연결 또는 실행 확인이 필수라면 `사용자 확인 필요`
4. 요청 범위와 필수 검증, 기록 파일과 인덱스 갱신까지 끝났다면 `완료`. 선택적 검증의 미실행은 이유와 영향을 별도로 적는다.

작업 완료에 필수인 검증과 참고용 후속 확인을 구분한다. 필수 검증이 남으면 안내만으로 완료 처리하지 않으며 GIT.md의 자동 전달 조건도 충족한 것으로 보지 않는다. Inspector 확인이 필요한 모든 Unity 작업을 무조건 미완료로 처리할 필요는 없다. 코드 작업 범위가 완료되었고 사용자의 확인 절차가 명확히 안내되었다면 실제 요청 범위에 따라 `완료` 또는 `사용자 확인 필요`를 선택한다.

## 15. 최종 체크리스트

- [ ] 프로젝트 루트와 `History` 폴더 위치를 확인했다.
- [ ] 기록 대상인 별개 작업은 새 HTML을 생성했고, 진행 중인 같은 작업의 보충은 해당 기록에 반영했다. commit 이후 Git 결과는 명시적 요청 없이 HTML에 자동 반영하지 않았다.
- [ ] 기존 작업 기록을 덮어쓰지 않았다.
- [ ] 작업 지시 시간, 완료 시간, 제목과 상태를 기록했다.
- [ ] 사용자 지시, 목표, 조건과 제한 사항을 기록했다.
- [ ] 판단 근거와 수행 과정을 검토 가능한 수준으로 요약했다.
- [ ] 생성, 수정, 삭제 및 확인만 한 파일을 구분했다.
- [ ] 테스트 결과와 수행하지 못한 검증을 구분했다.
- [ ] 실패 또는 남은 문제가 있다면 숨기지 않고 기록했다.
- [ ] 비밀 정보와 개인정보가 기록에 포함되지 않았다.
- [ ] `History.html`을 최신순으로 갱신했다.
- [ ] `History.html`에서 상세 기록 링크가 정상적인지 확인했다.
- [ ] Git 대상 작업이면 `GIT.md`에 따라 commit/push를 각각 판정하고 최종 commit ID·전송 결과를 실제 로그와 사용자 보고에 남겼다.
- [ ] commit 이후 HTML 후처리로 새 미커밋 기록을 자동 생성하지 않았다. 명시적인 기록 보완 요청이 있었다면 잔여 변경을 보고했다.
- [ ] 사용자에게 작업 결과와 기록 파일 경로를 보고했다.
