# Git 안전 및 자동 Commit/Push 규칙

이 문서는 AI 에이전트가 Git 저장소에서 파일을 생성하거나 수정할 때 따라야 하는 안전 규칙과 자동 commit/push 절차를 정의한다.

> **자동화 중심 정책:** 완료된 사용자 작업의 실제 프로젝트 파일 변경에 대해, HISTORY.md의 기록 조건과 이 문서의 각 안전 조건을 충족하면 별도의 추가 승인 없이 자동 commit 후 자동 push한다. commit과 push는 독립적으로 판정한다. 원격 저장소가 없거나 push 대상·권한·전송 범위를 안전하게 확정할 수 없으면 가능한 로컬 commit은 유지하고 push만 중지한다. 이력만 생성·보완하는 요청은 자동 commit/push로 확대하지 않는다.

---

## 1. 적용 범위

- Git 저장소 내부에서 수행하는 파일 생성, 수정 및 삭제 작업에 적용한다.
- 코드, 에셋, 설정, 문서 및 작업 이력 파일의 변경을 포함한다. 단, 이력 파일만 변경된 요청은 안전 규칙의 적용 대상이지만 자동 commit/push 대상은 아니다.
- 사용자가 직접 commit 또는 push 금지를 지시한 경우 해당 지시를 우선한다.
- 현재 경로가 Git 저장소가 아니면 commit이나 push를 시도하지 않는다. `git init`, 새 원격 저장소 생성, 최초 원격 연결은 별도의 명시적인 사용자 요청 없이는 수행하지 않는다.
- 파일 변경이 없는 분석, 설명 및 상태 확인 작업에는 commit과 push를 수행하지 않는다.

---

## 2. 작업 전 필수 확인

작업을 시작하기 전에 다음 명령을 실행하여 저장소 상태와 기존 변경 사항을 확인한다.

```bash
git status
git diff --stat
```

자동 commit/push를 수행할 작업에서는 다음 항목도 반드시 확인한다.

```bash
git rev-parse --show-toplevel
git branch --show-current
git remote -v
```

### 확인 목적

- 현재 위치가 올바른 Git 저장소인지 확인한다.
- 현재 브랜치를 확인한다.
- push할 원격 저장소와 upstream 설정이 존재하는지 확인하되, 원격이 없다는 이유만으로 안전한 로컬 commit까지 금지하지 않는다.
- 사용자가 이미 수정한 파일과 AI가 수정할 파일을 구분한다.
- 요청과 무관한 변경이 있는지 확인한다.
- 작업 범위가 예상보다 크지 않은지 확인한다.

기존 변경 사항이 있더라도 사용자 작업을 임의로 되돌리지 않는다. 이번 작업과 같은 파일의 같은 부분이 수정되어 안전하게 구분할 수 없다면 사용자에게 확인한다.

---

## 3. 작업 중 안전 규칙

- 요청과 무관한 변경을 되돌리지 않는다.
- 한 작업에 필요한 최소 파일만 수정한다.
- Unity CLI beta.16의 `unity vcs summarize --objects`, `unity vcs guid <guid>`, `unity vcs diff --full` 등은 Scene·Prefab·GUID에 대한 **선택적 읽기 전용 분석 수단**이다. 기존 Git의 상태·stage·commit·push 안전 규칙을 대체하지 않으며, 필요한 경우에만 실제 도움말을 확인해 사용한다.
- 사용자 요청과 관계없는 리팩터링, 파일 이동, 이름 변경 및 서식 변경을 하지 않는다.
- 사용자가 만들었거나 다른 작업에서 남은 변경을 AI 작업으로 간주하지 않는다.
- 파일을 수정하기 전에 기존 구조와 변경 이유를 확인한다.
- 변경 파일이 많아질 경우 실제 수정 전에 계획과 예상 범위를 설명한다.
- 자동 생성 파일, 빌드 산출물 및 캐시가 의도치 않게 포함되지 않는지 확인한다. Unity 프로젝트이면 7.1절에 따라 실제 Git 제외 규칙을 검사한다.
- 비밀번호, API 키, 인증 토큰, 인증서, 서비스 계정 파일 및 개인정보를 생성하거나 stage하지 않는다.

---

## 4. 금지되는 Git 명령과 작업

사용자의 명확한 별도 지시와 위험 확인 없이는 다음 작업을 수행하지 않는다.

```bash
git reset --hard
git clean -fd
git checkout -- <파일>
git restore --source=<커밋> <파일>
git push --force
git push --force-with-lease
```

다음 작업도 별도 사용자 승인 없이 실행하지 않는다.

- `git pull`
- `git rebase`
- `git merge`
- 브랜치 생성, 이름 변경 또는 삭제
- 태그 생성 또는 삭제
- 원격 저장소 추가, 변경 또는 삭제
- 커밋 수정(`git commit --amend`)
- 이미 공개된 커밋 기록 변경
- Stash 생성, 적용 또는 삭제

단순한 파일 복구 목적이라도 다른 사용자의 변경을 잃을 가능성이 있으면 실행하지 않는다.

---

## 5. 작업 후 필수 확인

작업을 마친 뒤 다음 명령으로 변경 상태를 확인한다.

```bash
git status
git diff -- <변경한 파일>
```

변경 파일이 여러 개면 각 경로를 명시하거나 관련 경로만 제한하여 확인한다.

```bash
git diff -- path/to/FileA.cs path/to/FileB.cs
git diff --check
```

### 확인 항목

- 요청한 파일만 변경되었는가?
- 예상하지 않은 삭제나 이름 변경이 없는가?
- `FILE.md`에 따라 **실제로 내용을 수정한 기존 텍스트 파일**의 의도적인 BOM·인코딩·줄바꿈 정규화인지 확인했는가? 예상된 전체 줄 diff는 원본 내용과 실제 수정사항을 비교해 검증하고, 수정 대상 밖의 파일까지 변경되었다면 중지한다.
- 디버그 코드, 임시 파일 또는 비밀 정보가 포함되지 않았는가?
- 작업 이력 HTML에 기록한 **작성 시점의** 작업·Git 상태와 현재 상태 문서가 실제 확인 결과에 부합하는가? commit/push 후 결과는 13절에 따라 최종 보고에 별도로 남긴다.
- 실행하지 않은 검증을 완료했다고 기록하지 않았는가?

### 5.1. beta.16 Unity Scene·Prefab 변경 분석 (선택)

Unity YAML의 오브젝트·컴포넌트·참조 차이를 상세히 확인할 필요가 있을 때, 설치된 Unity CLI에서 지원 여부를 먼저 조회한다.

```powershell
unity vcs --help
unity vcs summarize --help
unity vcs diff --help
unity vcs guid --help
```

- `unity vcs summarize --objects`로 비교 범위의 Scene·Prefab·에셋 변경을 오브젝트 단위로 확인할 수 있다. 긴 결과는 지원되는 `--full` 옵션을 검토한다.
- `unity vcs summarize --since main --to feature/login`은 **실제로 존재하는 Git 참조를 사용할 때** 작업 브랜치를 바꾸지 않고 범위를 요약하는 예시다. `main`과 `feature/login`을 현재 저장소에 반드시 있는 브랜치라고 가정하지 않는다.
- `unity vcs guid <guid>`로 참조 GUID의 에셋을 확인할 수 있다. `<guid>`는 자리 표시자이므로 실제 GUID로 교체하며, 특정 과거 커밋 조회는 지원되는 `--at` 옵션을 확인한다.
- `unity vcs diff --full`로 변경 오브젝트와 값을 상세 조회할 수 있으나 깊게 중첩된 일부 값은 여전히 축약될 수 있다. 결과만으로 Unity 에셋 참조가 완전하다고 단정하지 않는다.
- 이 검사는 **읽기 전용 보조 검증**에 한정하며 Git/Unity VCS의 commit·push·merge 등 쓰기 명령을 새로 승인하거나 자동 실행하지 않는다. 기존 `git diff` 및 `git diff --cached`, `.meta`·GUID 검사와 함께 사용한다.

## 6. 작업 이력 기록 완료 조건

HISTORY.md의 기록 대상인 실제 프로젝트 변경 작업은 commit 전에 다음 항목을 완료한다. 기록만 생성·보완하는 명시적 요청은 새 이력을 재귀적으로 만들지 않으며, 자동 Git 처리로 확대하지 않는다.

1. `HISTORY.md` 규칙에 따라 작업별 개별 HTML 파일을 생성한다.
2. `History/History.html`에 최신 작업 요약과 상세 기록 링크를 추가한다.
3. 작업 상태와 실제 변경 파일 목록을 정확히 기록한다.
4. 작업 범위 또는 기존 프로젝트 규칙에서 지정한 현재 상태 문서가 있는 경우에만 해당 문서를 갱신한다. 미지정 문서를 임의로 만들지 않는다.
5. 기록 내용과 실제 Git 변경 내역이 일치하는지 확인한다.

작업 기록과 인덱스 갱신이 누락된 상태에서는 자동 commit/push를 진행하지 않는다.

### 파일 변경이 없는 작업 예외

작업 이력 파일을 제외한 실제 파일 변경이 없는 분석, 설명 또는 상태 확인 작업은 다음과 같이 처리한다. 이력 생성 전에 판단하며, 이 예외와 명시적인 기록 요청의 처리는 `HISTORY.md`의 적용 범위를 따른다.

- 작업 기록 HTML을 새로 생성하지 않는다.
- `History/History.html`을 수정하지 않는다.
- commit과 push를 수행하지 않는다.
- 사용자에게 파일 변경이 없었음을 알린다.

이 예외는 파일이 실제로 변경되지 않은 읽기 전용 작업에만 적용한다.

## 7. Stage 전 필수 확인

commit 전에 다음 명령을 실행한다.

```bash
git status
git diff
git diff --cached
```

- `git diff`로 아직 stage하지 않은 변경을 확인한다.
- `git diff --cached`로 commit에 포함될 변경을 확인한다.
- 이미 stage되어 있던 사용자 변경이 있다면 이번 작업과 섞지 않는다.
- 사용자가 만든 기존 staged 변경을 자동으로 unstage하거나 수정하지 않는다.

### 7.1 Unity 프로젝트의 Git 제외 규칙 검사

Unity 프로젝트에서는 **stage 전에** `.gitignore`와 실제 Git 추적 상태를 확인한다. Git 저장소 루트와 Unity 프로젝트 루트가 다를 수 있으므로 두 경로를 먼저 확정하고, 저장소 상위·하위의 `.gitignore`, `.git/info/exclude`, 설정된 전역 제외 규칙의 실제 적용 결과를 구분한다.

1. Unity 프로젝트 루트의 `Assets/`, `Packages/manifest.json`, `ProjectSettings/ProjectVersion.txt`를 확인한다. Unity 프로젝트가 아니라면 이 절의 Unity 전용 검사를 생략한다.
2. 적용되는 `.gitignore`의 존재와 내용을 확인한다. 파일이 없거나 규칙이 부족하더라도 **다른 작업의 부수 효과로 새 `.gitignore`를 자동 생성·덮어쓰기·확대 수정하지 않는다.** 필요한 보완 사항을 보고한다. `.gitignore` 자체의 생성·보완을 요청받은 경우에는 기존 규칙, Git LFS 및 `.gitattributes`를 보존하면서 최소 변경만 수행한다.
3. 다음 경로가 Git에서 제외되는지 확인한다. 아래는 **Unity 프로젝트 루트에 놓인 `.gitignore`의 검사 참고 예시**이며, 모든 패턴을 새 프로젝트에 일괄 적용하라는 뜻이 아니다. Git 저장소 루트와 Unity 프로젝트 루트가 다르면 패턴의 기준 디렉터리를 실제 위치에 맞춰 해석한다.

```gitignore
# Unity 기본 생성 디렉터리 및 로컬 산출물
.utmp/
/[Ll]ibrary/
/[Tt]emp/
/[Oo]bj/
/[Bb]uild/
/[Bb]uilds/
/[Ll]ogs/
/[Uu]ser[Ss]ettings/
/[Mm]emory[Cc]aptures/
/[Rr]ecordings/

# IDE, 빌드 도구 및 UI Toolkit 생성 파일
.vs/
.gradle/
*.csproj
*.unityproj
*.sln
*.slnx
*.suo
*.userprefs
/UIElementsSchema/
/[Aa]ssets/[Ss]ceneDependencyCache*
```

4. Addressables를 사용한다면 다음처럼 **생성 결과로 확인된 파일만** 추가로 검사한다. 프로젝트의 Addressables 설정 자체나 사용자 소유 `link.xml`·StreamingAssets·ServerData를 자동 제외하지 않는다. 해당 항목의 용도와 재생성 가능 여부를 프로젝트별로 확인한다.

```gitignore
# Addressables 빌드에서 생성된 것으로 확인된 경우에 한해 참고
/[Aa]ssets/AddressableAssetsData/*/addressables_content_state.bin
/[Aa]ssets/AddressableAssetsData/*/addressables_content_state.bin.meta
/[Aa]ssets/Addressables_Temp/
/[Aa]ssets/StreamingAssets/aa/
```

5. `*.csproj`, `*.sln`, `*.slnx`, `.gradle/`, Addressables 경로 등은 **일반적인 Unity 자동 생성물일 때만** 제외 대상으로 판단한다. 수동 관리하는 솔루션·프로젝트 파일, Gradle 빌드 설정, 콘텐츠 갱신용 상태 파일, 커스텀 생성물이나 테스트용 산출물이면 기존 추적 정책을 우선하고 무조건 제외하지 않는다.
6. 실제 경로에 대해 `git check-ignore -v --no-index -- <경로>`로 어떤 제외 규칙이 적용되는지 확인한다. 해당 명령은 규칙과 일치하지 않으면 종료 코드 1을 반환할 수 있으므로, 그 결과를 일반적인 명령 실행 실패와 구분한다. 이미 추적 중인 파일은 `.gitignore`만 추가해도 자동으로 제외되지 않으므로 `git ls-files -- <경로>`로 별도 확인한다. 후보 경로가 실제 존재하지 않으면 **규칙 점검**과 **파일 존재·추적 상태 확인**을 구분해 보고한다.
7. **필수 프로젝트 자산은 제외하지 않는다.** `Assets/` 및 대응 `.meta`, `Packages/`의 의존성 파일, `ProjectSettings/`, UI Toolkit의 실제 UXML·USS·PanelSettings·폰트 에셋 등 프로젝트 재현에 필요한 파일은 추적 대상으로 취급한다. 생성된 캐시와 실제 소스 에셋을 파일명만 보고 혼동하지 않는다.
8. **이번 작업의 stage 후보**에 생성 폴더나 비밀 정보가 포함되었다면 자동 stage·commit을 중지하고 경로와 원인을 보고한다. 작업과 무관하게 이미 추적 중인 생성 폴더는 위험을 보고하되, 이번 변경과 분리 가능한 경우 안전한 파일의 commit까지 일괄 중지하지 않는다. `git rm --cached`, `git add -f`, 저장소 전체 `.gitignore` 재작성, 기존 LFS 규칙 삭제를 임의로 실행하지 않는다.
9. 해당 작업의 대상 파일이 Git에서 의도치 않게 제외된다면 먼저 제외 원인을 확인하고, `git add -f`로 무시 규칙을 우회하지 않는다.

참고: [GitHub Unity.gitignore 예시](https://github.com/github/gitignore/blob/main/Unity.gitignore) 및 현재 프로젝트의 실제 Git 규칙. Unity Version Control(UVCS)의 `ignore.conf` 지침을 Git `.gitignore`의 적용 결과와 동일한 것으로 취급하지 않는다.

## 8. 최소 범위 Stage 규칙

이번 작업에서 생성·수정·삭제한 파일만 경로를 명시하여 stage한다. 경로를 지정하는 것만으로 해당 파일의 사용자 변경이 제외되는 것은 아니다.

- 작업 시작 시 staged/unstaged 변경을 모두 확인하여 기존 변경과 이번 변경을 구분한다.
- 같은 파일에 기존 사용자 변경이 있으면 겹치지 않는 변경도 파일 전체를 `git add`하지 않는다.
- 변경 구간 단위로 이번 변경만 안전하게 stage할 수 있는지 확인한다. 분리가 불확실하면 자동 commit을 중지한다.
- 기존 사용자 staged 변경을 임의로 unstage하지 않는다. 이번 작업만 커밋하도록 안전하게 분리할 수 없다면 현재 상태를 보존하고 중지 이유를 보고한다.

```bash
git add -- path/to/FileA.cs path/to/FileB.cs
git add -- History/작업기록.html History/History.html
```

특별한 이유 없이 다음과 같이 저장소 전체를 stage하지 않는다.

```bash
git add .
git add -A
```

stage 후 반드시 다음 명령으로 실제 포함 내용을 다시 확인한다.

```bash
git status
git diff --cached --stat
git diff --cached
```

확인 결과 무관한 파일이 포함되어 있으면 commit하지 않는다. 사용자의 staged 변경을 손상하지 않는 안전한 방법으로 이번 작업의 파일만 분리할 수 있는지 검토하고, 불확실하면 사용자에게 확인한다.

## 9. 비밀 정보 검사

commit 전에 변경 파일 이름과 실제 diff를 확인하여 다음 정보가 포함되지 않았는지 검사한다.

- 비밀번호
- API 키
- 인증 토큰
- 개인 키와 인증서
- 서비스 계정 파일
- 실제 운영 서버 접속 정보
- 개인정보
- 로컬 환경 전용 `.env` 파일

비밀 정보 또는 비밀일 가능성이 있는 값이 변경 목록에 있으면 다음과 같이 처리한다.

1. 자동 commit/push를 중지한다.
2. 비밀 값을 사용자 응답이나 작업 기록에 그대로 노출하지 않는다.
3. 발견한 파일 경로와 중지 이유만 사용자에게 알린다.
4. 사용자의 안전한 처리 지시를 기다린다.

## 10. Commit 규칙

다음 조건을 모두 충족하면 별도의 추가 승인 없이 이번 작업의 변경 사항을 commit한다.

- 사용자가 지시한 작업이 완료되었다.
- 저장소 파일이 실제로 변경되었다.
- 작업 이력과 인덱스 갱신이 완료되었다.
- 이번 작업의 파일만 stage되었다.
- 비밀 정보가 포함되지 않았다.
- 가능한 테스트와 검증 결과를 확인했다.
- 사용자가 commit을 금지하지 않았다.

**로컬 commit은 원격 저장소 설정과 독립적으로 실행한다.** 원격이 없거나 upstream이 불명확하더라도 위 조건이 모두 충족되면 commit을 완료하고, push만 11절에 따라 미수행으로 보고한다. Git 저장소가 아니면 commit도 수행하지 않는다.

commit 메시지는 작업 목적을 알 수 있도록 짧고 구체적으로 작성한다.

```bash
git commit -m "플레이어 이동 오류 수정"
git commit -m "로그인 패널 UI 로직 추가"
git commit -m "Git 안전 규칙 문서 추가"
```

프로젝트에서 Conventional Commits 등 기존 메시지 형식을 사용하고 있다면 해당 형식을 우선한다.

```bash
git commit -m "fix: 캐릭터 이동 오류 수정"
git commit -m "docs: Git 안전 규칙 추가"
```

커밋이 성공했는지 명령 결과와 새 커밋 ID를 확인한다.

## 11. Push 규칙

**자동화 중심 정책:** commit 성공 후 아래 push 안전 조건이 모두 충족되면 별도의 추가 승인 없이 현재 브랜치의 확인된 원격 브랜치로 push한다. 일부 조건이 불충족이면 **push만 중지**하고, 이미 완료한 로컬 commit과 사용자 작업 상태는 보존한다. 중지·미시도는 실행 실패와 구별한다.

### 11.1 원격 및 대상 브랜치 확인

commit 전 초기 상태와 commit 후 상태를 비교하고, push 직전에 다음 내용을 다시 확인한다.

```bash
git branch --show-current
git remote -v
git rev-parse --abbrev-ref --symbolic-full-name '@{upstream}'
```

- 현재 브랜치가 분리된 HEAD 상태이면 자동 push하지 않는다. `@{upstream}` 조회는 미설정 시 실패할 수 있으며 이를 원격 설정 변경의 허가로 취급하지 않는다.
- 사용자가 **이 작업에 대해** 원격·대상 브랜치를 명시했다면 그 지시와 실제 Git 설정을 대조한다. 지정이 없으면 현재 브랜치의 확인된 upstream을 사용한다. `origin`이라는 이름, 단일 원격 존재, Git의 `push.default` 설정만으로 새 push 대상을 추정하지 않는다.
- 자동 push 대상은 원칙적으로 **현재 로컬 브랜치와 같은 이름의 원격 브랜치**로 제한한다. 다른 브랜치를 지정해야 한다면 사용자의 명시적인 지시가 필요하다.
- 확인한 원격의 push URL, fetch URL과 브랜치 추적 설정을 확인한다. 자격 증명이 URL에 포함되어 있으면 로그·HTML·사용자 응답에 노출하지 않는다. 실제 push 대상 저장소가 fetch로 검증한 저장소와 다르거나 관계를 확인할 수 없다면 push하지 않는다.
- 원격 저장소가 없거나, **사용자가 대상을 명시하지 않았고** upstream/대상 브랜치가 불명확하거나, 원격 브랜치가 아직 없다면 **로컬 commit만 유지하고 push하지 않는다**. 원격 추가, upstream 설정, 새 원격 브랜치 게시(`-u` 포함)를 자동 수행하지 않는다.

### 11.2 원격 상태와 전송 범위 검증

원격과 브랜치를 안전하게 확정한 경우 다음 순서로 확인한다. 예시의 `<확정한-원격>`과 `<확정한-대상브랜치>`는 사전에 확인한 실제 값으로 바꾼다. 자동화 기본값에서는 대상 브랜치가 현재 브랜치와 동일하며, 사용자가 다른 대상을 명시한 경우에만 예외로 처리한다.

```bash
# push 대상 브랜치가 원격에 실제 존재하는지 확인
git ls-remote --exit-code <확정한-원격> refs/heads/<확정한-대상브랜치>

# 원격 추적 정보 갱신 (pull, merge, rebase 아님)
git fetch --no-tags <확정한-원격>

# 로컬에서 비교할 원격 추적 ref의 존재 여부 확인
git rev-parse --verify refs/remotes/<확정한-원격>/<확정한-대상브랜치>

# 원격 브랜치가 현재 HEAD의 조상인지 확인 (종료 코드 0이어야 함)
git merge-base --is-ancestor refs/remotes/<확정한-원격>/<확정한-대상브랜치> HEAD

# 이번 push에 포함될 전체 커밋 및 최종 차이 확인
git log --oneline refs/remotes/<확정한-원격>/<확정한-대상브랜치>..HEAD
git diff --stat refs/remotes/<확정한-원격>/<확정한-대상브랜치>..HEAD
# 민감정보·무관한 수정 포함 여부를 확인할 때 상세 diff도 검사
git diff refs/remotes/<확정한-원격>/<확정한-대상브랜치>..HEAD
```

- `git fetch`는 확인된 원격에 대한 **원격 추적 정보 갱신 용도**로만 허용한다. 브랜치 체크아웃, pull, merge, rebase, prune, 강제 동기화 등은 자동 실행하지 않는다.
- 원격 브랜치의 실제 SHA(`ls-remote`)와 fetch 이후의 해당 원격 추적 ref가 일치하는지 확인한다. refspec 또는 권한 문제로 일치 여부를 검증할 수 없다면 push하지 않는다. 원격 브랜치가 변경된 것으로 확인되면 상태를 재확인하고 안전하지 않다면 중지한다.
- `merge-base --is-ancestor`가 실패하거나 로컬 브랜치가 원격보다 뒤처져 있거나 분기되었다면 push하지 않는다. 사용자 동의 없이 기록을 변경하거나 자동 병합하지 않는다.
- `git log <원격추적-ref>..HEAD --oneline`에 **이번 작업 외 미전송 커밋**이 있으면 사용자 지시 없이 함께 push하지 않는다. 다른 커밋을 삭제·재작성해 범위를 줄이지 않는다.
- 원격 확인 또는 fetch에 실패하여 **전체 전송 범위**를 확인할 수 없으면 push를 중지한다. 로컬 캐시만으로 원격 최신 상태를 확인했다고 주장하지 않는다.
- 브랜치 보호·필수 리뷰·Pull Request·CI 정책이 **확인된 경우** 이를 우회하지 않는다. 적용되는 보호 정책이 있음을 알지만 준수 여부를 확인할 수 없다면 push를 중지한다. 보호 정책의 존재가 별도로 확인되지 않는다는 이유만으로 모든 자동 push를 일괄 중지하지는 않되, 보호 정책을 검증했다고 주장하지 않는다. 원격에서 정책 위반으로 거부되면 즉시 중지한다.
- 위 검사는 **검사 시점의 원격 상태**만 보여준다. 확인 직후 다른 사용자가 원격 브랜치를 갱신할 수 있으므로, 검사 성공만으로 push 성공이나 원격 상태의 고정을 보장하지 않는다. 원격 갱신으로 일반 push가 거부되면 강제 전송이나 자동 재시도 없이 중지하고 현 상태를 보고한다.

### 11.3 자동 Push 실행과 결과 확인

위 조건이 모두 충족되면 다음 형식으로 push한다.

```bash
git push <확정한-원격> HEAD:refs/heads/<확정한-대상브랜치>
```

- `--force`, `--force-with-lease`, `--set-upstream`/`-u`, 임의 브랜치 변경은 사용하지 않는다. 브랜치 생성·태그 전송을 자동으로 추가하지 않는다.
- push 명령의 종료 코드와 출력을 확인한다. 가능하면 `git ls-remote --exit-code <확정한-원격> refs/heads/<확정한-대상브랜치>`로 사후 원격 커밋 ID를 확인한다. 사후 원격 HEAD가 이번 HEAD와 다르더라도 이후 다른 사용자가 새 커밋을 전송한 것일 수 있으므로, push 실행 결과와 사후 조회 결과를 구분하여 보고한다. 사후 조회가 불가하면 명령 성공과 원격 재확인 불가를 구분한다.
- 원격을 확인한 직후에도 다른 사용자의 push로 일반 push가 거부될 수 있다. 거부되면 **그 시도의 결과를 실패로 기록하고 즉시 중지**한다. 자동 재시도, 원격 설정 변경, `--force`/`--force-with-lease`, pull·merge·rebase를 수행하지 않는다. 로컬 commit을 유지하고 변경된 원격 상태 및 후속 조치 필요 여부를 안내한다.
- 네트워크 단절 등으로 push 결과 자체가 불명확하다면 성공·실패를 임의로 단정하지 않고 `확인 불가`로 보고한다. 읽기 전용 원격 조회로 반영 여부를 확인할 수 있지만, 추가 push는 자동 실행하지 않는다.

### 11.4 원격이 없는 프로젝트의 처리

- Git 저장소이며 10절의 조건을 충족하면 **자동 commit까지 정상 수행**한다.
- 원격 또는 검증 가능한 대상 브랜치가 없다면 **push는 미수행(설정 필요)**으로 기록한다. upstream이 없어도 사용자가 원격·대상 브랜치를 명시했고 나머지 모든 검증이 가능하면 해당 명시적 지시를 따를 수 있다. 이를 commit 실패나 push 실행 실패로 표시하지 않는다.
- 원격 저장소 생성, 연결, 브랜치 게시, 보호 규칙 변경은 이 문서의 자동 작업 범위에 포함하지 않는다. 사용자 별도 지시가 있을 때 관련 안전 절차를 적용한다.

## 12. 자동 Commit/Push 적용 조건

자동 commit/push 규칙은 완료된 사용자 작업에만 적용한다.

| 상황 | Commit | Push | History 기록 |
|---|---:|---:|---:|
| 요청한 실제 프로젝트 파일 변경 작업 완료 | 10절 조건 충족 시 자동 수행 | 11절 조건 충족 시 자동 수행 | 수행 |
| 원격 없음·push 대상 미확정·원격 브랜치 미존재 | 조건 충족 시 자동 수행 | 미수행(설정 필요) | 수행 |
| 원격 분기·다른 미전송 커밋·보호 정책 또는 검증 불가 | 조건 충족 시 자동 수행 | 미수행(안전 조건 미충족) | 수행 |
| 이력만 생성·보완하도록 요청 | 명시적 Git 지시가 있을 때만 | 명시적 Git 지시가 있을 때만 | 요청한 기록만 수행 |
| 파일 변경 없이 분석·설명만 수행 | 수행 안 함 | 수행 안 함 | 수행 안 함 |
| 작업 부분 완료 | 원칙적으로 중지 | 중지 | 부분 완료로 기록 |
| 필수 테스트 또는 필수 사용자 확인이 남음 | 중지 | 중지 | 사용자 확인 필요로 기록 |
| 비밀 정보 발견 | 중지 | 중지 | 비밀 값 없이 원인 기록 |
| commit 실패 | 실패 | 수행 안 함 | 사전 HTML 유지, 실제 실패 원인은 최종 보고 |
| push 실패 | commit 상태 유지 | 실패 | 사전 HTML 유지, 실제 결과는 최종 보고 |
| Git 저장소가 아님 | 수행 불가 | 수행 불가 | 파일 변경 작업이면 기록 |

자동화에는 commit/push와 이를 위한 읽기 전용 검사 및 확정한 원격에 대한 fetch만 포함한다. 원격 연결·upstream 설정·브랜치 생성, 기록 재작성, pull·merge·rebase 등은 포함하지 않는다. commit과 push는 독립 판정하며, push 보류가 안전한 로컬 commit을 무효화하지 않는다.

## 13. 실패 처리 규칙

commit 또는 push가 실패하면 성공했다고 기록하거나 보고하지 않는다. **Git 후처리의 최종 결과는 Git 로그와 사용자 최종 보고를 기준으로 한다.** 기록 대상 작업에서 생성된 HTML은 기본적으로 commit 전의 실행 결과와 그 시점의 Git 상태를 담는다.

최종 보고에 포함하기 위해 반드시 다음 내용을 확인한다.

- 실패한 단계: stage, commit 또는 push
- 핵심 오류 내용
- 실제로 생성된 commit의 존재 여부
- 로컬 변경이 남아 있는지 여부
- 원격 저장소에 반영되었는지 여부
- 사용자가 다음에 수행해야 할 조치

### Commit 실패

- push를 시도하지 않는다.
- 오류 해결을 위해 사용자 Git 설정을 임의로 변경하지 않는다.
- 로컬 변경과 stage 상태를 보존한다.

### 후처리 기록과 추가 commit

- commit **이전에** 생성하는 History HTML에는 `Commit: 미실행 (기록 작성 시점)`, `Push: 미실행 (기록 작성 시점)`으로 적는다. 이는 **최종 Git 결과가 아니라 당시 스냅샷**이다. 자동 Git 처리의 실행 여부·실패·성공을 미리 예상해 기록하지 않는다.
- commit 또는 push가 끝난 **후에는 성공·실패·중지 여부와 관계없이 기존 History HTML 및 인덱스를 자동으로 다시 수정하지 않는다.** 최종 commit ID는 Git 로그와 사용자 최종 보고에, push 성공·실패·미수행·확인 불가는 사용자 최종 보고에 남긴다. Git 작업 자체가 실패하더라도 HTML 갱신 때문에 새로운 미커밋 변경을 만들지 않는다.
- commit을 시도하기 **전에** Git 처리가 안전 조건 미충족으로 보류될 것이 확정된 경우에는, 기록과 Stage 전에 실제 미수행 사유를 HTML에 반영할 수 있다. 미시도를 실행 실패로 표현하지 않는다. 이후에도 Git 절차를 자동 재시도하지 않는다.
- 예외적으로 사용자가 **명시적으로** 동일 작업의 Git 후속 결과를 HTML에 추가해 달라고 요청하면 기존 상세 기록과 인덱스를 보완할 수 있다. 그 보완은 기록 자체의 변경으로 취급하며 **자동 추가 commit/push를 유발하지 않는다.** 발생한 미커밋 기록과 staged/unstaged 상태를 사용자에게 보고한다.
- 성공 기록을 남기기 위해 반복 commit/push하거나 `git commit --amend`를 수행하지 않는다. 앞선 commit ID를 이후 기록 보완에 참조할 수 있지만, 보완 기록 자신의 commit ID를 같은 commit에 넣기 위한 반복 처리는 하지 않는다.

### Push 실패 또는 안전 조건 미충족

- push를 실제 실행했으나 오류가 난 상태와, 원격 없음·검증 불가 등으로 **push를 시도하지 않은 상태**를 구분한다.
- commit이 로컬에 생성되었는지 확인한다.
- 자동으로 pull, rebase, merge 또는 Force Push를 수행하지 않는다.
- 원격 반영 실패 사실과 로컬 commit 상태를 사용자에게 알린다.

## 14. 작업 완료 보고

파일이 변경된 Git 작업을 완료하면 사용자에게 다음 내용을 보고한다.

- 생성, 수정 및 삭제한 파일
- 수행한 테스트와 검증 결과
- 생성한 작업 기록 HTML 경로
- 갱신한 `History/History.html` 경로
- commit 성공 여부와 commit ID
- commit 메시지
- push 성공 여부
- push한 원격 저장소와 브랜치(실제로 수행한 경우)
- 원격 없음·push 대상 미확정·보호 정책 등으로 push하지 않은 경우의 미수행 사유와 로컬 commit의 유지 상태
- 실패하거나 확인하지 못한 항목(History HTML을 commit 후 자동 수정하지 않았는지 및 별도 미커밋 변경의 존재 여부 포함)

실제로 수행하지 않은 commit, push 또는 테스트를 완료했다고 표현하지 않는다.

## 15. 표준 작업 순서

```text
사용자 지시 확인
    ↓
git status / git diff --stat
    ↓
기존 변경과 작업 범위 확인
    ↓
필요한 최소 파일만 수정
    ↓
테스트 및 결과 검토
    ↓
상세 작업 기록 HTML 생성
    ↓
History/History.html 갱신
    ↓
git status / git diff 확인
    ↓
Unity 프로젝트라면 .gitignore·추적 상태 확인
    ↓
이번 작업 파일만 경로를 명시하여 stage
    ↓
git diff --cached 확인
    ↓
비밀 정보 검사
    ↓
commit
    ↓
원격/대상 브랜치/미전송 커밋·보호 정책 확인
    ↓
안전 조건 충족: 일반 git push <확정한-원격> HEAD:refs/heads/<확정한-대상브랜치>
조건 미충족: push 생략, 로컬 commit 유지
push 거부 또는 결과 불명확: 자동 재시도 없이 중지
    ↓
Git 로그·push 결과 확인 (History HTML은 commit 후 자동 수정하지 않음)
    ↓
실제 결과 사용자 보고
```

## 16. 최종 체크리스트

- [ ] 작업 전 `git status`와 `git diff --stat`을 확인했다.
- [ ] 현재 저장소, 브랜치 및 원격 저장소를 확인했다. 원격이 없다면 로컬 commit과 push를 별도로 판정했다.
- [ ] 사용자 또는 다른 작업의 기존 변경을 보존했다.
- [ ] 요청에 필요한 최소 파일만 수정했다.
- [ ] Unity 프로젝트라면 `.gitignore`의 적용 범위, `.utmp`·Gradle·IDE·SceneDependencyCache·조건부 Addressables 생성물 및 이미 추적 중인 파일을 확인했다. 실제 소스 에셋을 무조건 제외하지 않았다.
- [ ] 위험하거나 파괴적인 Git 명령을 사용하지 않았다.
- [ ] 작업별 HTML 기록과 `History/History.html` 갱신을 완료했다.
- [ ] commit 전 `git status`, `git diff`, `git diff --cached`를 확인했다.
- [ ] 이번 작업에서 변경한 경로만 명시적으로 stage했다.
- [ ] 비밀 정보가 변경 목록에 없는지 확인했다.
- [ ] commit 메시지가 작업 목적을 구체적으로 설명한다.
- [ ] commit 결과와 commit ID를 확인했다.
- [ ] push 대상 원격·브랜치·원격 추적 ref·전체 미전송 커밋을 확인했다.
- [ ] 보호 정책 및 원격과 로컬의 분기 여부를 확인하고, Force Push 없이 안전한 경우에만 현재 브랜치로 push했다.
- [ ] push 실행 성공·실패·미수행·확인 불가를 구분하여 결과를 확인했다. 원격 경쟁 갱신으로 거부되면 자동 재시도하지 않았다.
- [ ] commit 이후 History HTML/인덱스를 Git 결과 기록을 위해 자동 변경하지 않았고, 실패 또는 미확인 항목을 최종 보고에 실제 상태대로 남겼다.
