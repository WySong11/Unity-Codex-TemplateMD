Codex 규칙 템플릿 안내서

현재 템플릿 ZIP의 13개 프로젝트용 파일이 각각 무엇을 담당하는지, 서로 어떻게 연결되는지, 새 Unity 프로젝트에 어떤 순서로 적용해야 하는지 설명합니다. Unity CLI 1.0.0-beta.17의 Plugin 의존성·Skill 상태·자동화 변경까지 반영했습니다.

총 13개 파일진입 문서 2개개발·운영 규칙 7개도구 설정 파일 4개오프라인 HTMLCLI beta.17 기준
01 / 개요

이 압축파일은 무엇인가?

Unity 6 계열 프로젝트에서 VS Code + Codex를 사용할 때, 코드·에셋·빌드·기록·Git 작업에 공통 규칙을 적용하도록 만든 프로젝트용 지침 묶음입니다. 파일들은 서로 연결되어 있지만, 모든 작업에서 13개를 전부 읽을 필요는 없습니다.

①

진입 문서

AGENTS.md가 원칙을 선언하고 READ.md가 필요한 상세 문서를 찾아줍니다.

2개 · 시작점과 라우팅
②

개발·운영 규칙

C#·에셋·파일 형식·Unity 도구·빌드·History·Git의 세부 기준을 담당합니다.

7개 · 실제 작업 절차
③

설정 파일

편집기, Git, VS Code가 실제로 어떤 파일 형식과 추적 정책을 사용할지 보조합니다.

4개 · 도구 환경 설정
i

구분해야 할 점 Markdown 규칙 파일을 복사하는 행위 자체가 Unity CLI 업데이트·MCP 연결·빌드·Commit을 즉시 실행하는 것은 아닙니다. 실제 프로젝트 작업을 수행하는 Codex가 해당 규칙을 적용할 때 조건에 맞는 절차가 실행됩니다.

i

Unity CLI beta.17 변경 Plugin 설치·업그레이드 시 의존 Plugin 설치와 베타 경고를 확인해야 합니다. unity skill refresh --dry-run --format json은 갱신 전 상태를 살펴보는 미리보기이며 실제 Skill 갱신은 별도 승인 대상입니다. Pipeline TSV 출력 및 일부 CLI 종료 코드가 변경되었지만 기존 CLI·Pipeline 자동 최신화 정책은 유지됩니다. 자세한 절차는 UNITY_TOOLING.md를 참고하세요.

02 / 파일 구성

폴더 구조와 배치 위치

압축을 해제한 뒤 Unity 프로젝트의 실제 루트에 아래처럼 배치합니다. 실제 루트는 Assets/, Packages/, ProjectSettings/ 폴더가 있는 위치입니다.

MyUnityProject/ ├── AGENTS.md ← 프로젝트 규칙 진입점 ├── .editorconfig ← 에디터의 인코딩·줄바꿈 ├── .gitattributes ← Git 줄바꿈 속성 ├── .gitignore ← Unity 생성 파일 제외 ├── .vscode/ │ └── settings.json ← VS Code 기본 LF ├── MD/ │ ├── READ.md ← 작업별 문서 안내 │ ├── FILE.md ← 인코딩·줄바꿈 │ ├── UNITY_CS_CODING_RULES.md ← C# 규칙 │ ├── UNITY_ASSET_RULES.md ← 씬·프리팹·에셋 │ ├── UNITY_TOOLING.md ← CLI·MCP·Pipeline │ ├── BUILD.md ← 빌드·검증 │ ├── HISTORY.md ← HTML 작업 이력 │ └── GIT.md ← 안전한 Commit·Push ├── Assets/ ← 기존 Unity 프로젝트 ├── Packages/ └── ProjectSettings/

파일 수: 루트의 AGENTS.md 1개 + MD/ 문서 8개 + 설정 파일 4개 = 총 13개. History/는 실제 기록 대상 작업에서 규칙에 따라 생성하는 폴더이며 ZIP에 미리 들어 있지 않습니다.

03 / 설치

새 Unity 프로젝트에 적용하는 방법

STEP 01

Unity 프로젝트 루트 확인

Unity Editor 또는 파일 탐색기에서 Assets·Packages·ProjectSettings가 함께 있는 폴더를 찾습니다.

STEP 02

기존 설정과 Git 변경 보호

기존 AGENTS.md, .editorconfig, .gitattributes, .gitignore 및 VS Code 설정을 확인합니다. 기존 파일은 덮어쓰지 않고 병합합니다.

STEP 03

템플릿 파일 배치

AGENTS.md를 루트에, 8개 상세 MD를 MD/에, 설정 파일을 각 상대 경로에 둡니다. 숨김 파일이 누락되지 않았는지 확인합니다.

STEP 04

Codex Plugin·Skill 상태 확인

Unity CLI beta.16의 unity setup codex는 Plugin과 Unity Skill을 함께 구성합니다. 사용자 승인 후 설치하며, Plugin·Skill·MCP·Pipeline을 각각 구분해서 점검합니다.

STEP 05

첫 실제 Unity 작업 수행

세션 첫 실제 Unity 작업에서 UNITY_TOOLING.md에 따라 도구를 점검하고, 관련 MD를 읽어 최소 변경 및 테스트를 수행합니다.

STEP 06

History 및 Git 결과 확인

실제 프로젝트 변경 시 작업별 HTML 기록을 남깁니다. 안전 조건 충족 시 자동 Commit·Push하고 결과를 확인합니다.

PowerShell · 처음 확인할 명령 예시
# 실제 Unity 프로젝트 루트에서 실행
$UnityProjectRoot = (Get-Location).ProviderPath
Test-Path -LiteralPath (Join-Path $UnityProjectRoot 'Assets')
Test-Path -LiteralPath (Join-Path $UnityProjectRoot 'Packages/manifest.json')
Test-Path -LiteralPath (Join-Path $UnityProjectRoot 'ProjectSettings/ProjectVersion.txt')

# Git 저장소인 경우 기존 변경 확인
git status --short

# Unity CLI 및 beta.16 Codex Plugin·Skill 설치 예정 사항 확인
unity --version
unity setup codex --dry-run
# 실제 Plugin·Skill 설치는 사용자 승인 후: unity setup codex
!

자동화 범위 확인 이 템플릿의 GIT.md는 조건이 허용되면 자동 Commit·Push를 수행하도록 작성되어 있습니다. 협업 프로젝트라면 원격 저장소·브랜치·승인 정책을 먼저 검토하세요. 공식 Unity Plugin 설치도 별도 사용자 승인 대상입니다.

i

Unity CLI beta.16 적용 기존 unity pipeline editors·unity pipeline upgrade 명령은 유지됩니다. 신규 unity skill sync codex는 승인 후 사용하며, unity command editor dialog로 팝업을 조회할 수 있습니다(지원 Editor). 열린 Editor 빌드와 unity vcs summarize --objects는 BUILD.md·GIT.md의 조건에 따라 선택적으로 사용합니다. Unity 공식 릴리스 노트

06 / 파일별 설명

각 파일의 역할과 사용 방법

모든 파일은 실제 ZIP의 내용을 기준으로 정리했습니다. 상세 설명은 원문을 대체하지 않으므로 구현 시에는 반드시 해당 MD의 실제 규칙을 함께 확인하세요.

01 / 13  ·  진입 문서

AGENTS.md

프로젝트 규칙 총괄

원본 파일 열기 ↗

적용 범위·작업 승인·문서 연결·UI Toolkit 기본 방향·기록 및 Git 처리 조건을 한곳에서 안내합니다.

언제 사용하는가

프로젝트를 처음 열 때, 실제 프로젝트 작업을 시작하기 전에

주요 운영 원칙
  • 신규 UI의 기본 방향은 UI Toolkit이며 기존 uGUI/TMP 화면은 임의로 전환하지 않음
  • 실제 수정 파일에는 FILE.md 목표 인코딩·줄바꿈 적용
  • AGENTS.md가 도구 권한이나 승인 정책을 무시하게 만들지는 않음

실제 사용 방법

  1. Unity 프로젝트 루트(Assets / Packages / ProjectSettings가 있는 위치)에 둡니다.
  2. 작업 시작 전에 AGENTS.md를 확인한 후 MD/READ.md에서 해당 작업의 세부 규칙을 찾습니다.
  3. VS Code + Codex에서 공식 unity-agent-plugin과 별도 Unity Skill 설치·인식 상태를 각각 확인합니다. 설치가 필요하면 사용자 승인 후 unity setup codex를 실행하고 중복 Skill을 검사합니다.
  4. 요청한 기능 작업이 끝나면 검증 → History 기록 → Git 후처리 규칙을 적용합니다.
주의파일만 복사했다고 Codex가 Unity Plugin·MCP를 설치하거나 Unity Editor에 연결된 것은 아닙니다.
함께 보는 파일READ.md ↗ UNITY_TOOLING.md ↗ GIT.md ↗

언제 사용하는가

새 프로젝트 참여 시, 작업 목적이 바뀔 때

주요 운영 원칙
  • 읽는 순서는 우선순위를 뜻하지 않음
  • VALIDATION.md와 Batch/Validate.ps1은 선택적이며 현재 ZIP에 없음
  • 문서 설명 요청만으로 업데이트·빌드·Push를 실행하지 않음

실제 사용 방법

  1. AGENTS.md를 읽은 다음 READ.md의 작업별 읽는 순서 표를 확인합니다.
  2. C# 구현이면 C# 규칙·FILE.md를, UI Toolkit이면 C#·에셋·FILE.md를 함께 확인합니다.
  3. 실제 파일을 바꾸는 작업이면 HISTORY.md와 GIT.md 적용 조건도 검토합니다.
주의문서에 적힌 예시 경로나 버전을 현재 프로젝트의 실제 값으로 취급하지 마세요.
함께 보는 파일AGENTS.md ↗ FILE.md ↗
03 / 13  ·  운영 규칙

MD/UNITY_TOOLING.md

Unity CLI · MCP · Pipeline

원본 파일 열기 ↗

Unity CLI의 현재 채널 최신 확인, Codex MCP 등록 점검, 프로젝트별 com.unity.pipeline 설치·업데이트, Editor 연결 확인을 정의합니다.

언제 사용하는가

세션의 첫 실제 Unity 구현·수정·실행·검증 작업 직전 / 연결 오류 / 사용자 직접 점검 요청

주요 운영 원칙
  • 최초 실제 Unity 작업 전 전체 점검은 세션당 한 번
  • 후속 작업마다 전체 최신 조회를 반복하지 않음
  • CLI와 Pipeline 자동 최신화 유지: 사용자·팀의 명시적 고정, 호환 불가, 확인 불가, 권한 제한은 예외
  • beta.16에서는 Plugin과 Unity Skill을 별도로 확인하고, 신규 설치 또는 Skill 동기화는 사용자 요청·승인 대상

실제 사용 방법

  1. VS Code 터미널이 실제 Unity 프로젝트 루트에 있는지 확인합니다.
  2. Unity CLI의 버전 및 업데이트를 확인하고 조건이 맞으면 같은 채널 최신으로 갱신합니다. beta.16의 unity skill sync --help로 Skill 상태 관리 방법을 확인하되 사용자 승인 없이 동기화를 실행하지 않습니다.
  3. Unity MCP 등록 상태를 검사하고 누락된 경우 dry-run 검토 후 관련 지침대로 보완합니다.

  3. C# BOM과 Batch CRLF처럼 확장자별 저장 규칙은 .editorconfig 및 FILE.md에 따라 별도 확인합니다.
주의이미 settings.json에 디버깅·확장 설정 등이 있다면 해당 값을 삭제하지 말고 병합해야 합니다.
함께 보는 파일.editorconfig ↗ FILE.md ↗

※ ‘원본 파일 열기’는 안내서 HTML을 원본 템플릿 파일들과 같은 상대 폴더 구조로 보관한 경우에만 정상적으로 연결됩니다. 이 안내서와 원본을 함께 담은 ZIP을 사용하면 됩니다.

08 / 저장 형식

인코딩과 줄바꿈 규칙 한눈에 보기

FILE.md에서 선언하고 .editorconfig 및 .gitattributes로 보조하는 정책입니다. 신규 파일과 실제 내용을 수정한 기존 파일에 적용하며, 자동 생성 파일은 예외입니다.

파일 유형인코딩 목표줄바꿈 목표적용 기준
.csUTF-8 with BOMLF (\n)신규 생성 또는 기존 내용 수정
.md .json .uxml .uss .shaderUTF-8 without BOMLF (\n)신규 생성 또는 기존 내용 수정
.bat .cmdUTF-8 without BOM 기본CRLF (\r\n)신규 생성 또는 기존 내용 수정
.unity .prefab .meta 등Unity/도구 원래 형식Unity/도구 원래 형식생성·관리 도구 형식 보존
!

점진적 형식 통일 예를 들어 이전에 CRLF·BOM 없음으로 저장한 Player.cs도 실제 코드 내용을 수정하면 UTF-8 BOM + LF로 저장합니다. 단, 작업과 무관한 파일 전체를 한 번에 변환하지 않으며, 프로젝트 설정과 충돌하면 변환을 보류합니다.

Git · 파일별 실제 줄바꿈과 제외 규칙 확인
# 파일에 적용되는 Git 속성 확인
git check-attr text eol -- Assets/Scripts/PlayerController.cs

# Git이 파일을 제외하는 이유 확인
git check-ignore -v --no-index -- Library/ExampleCache

# 변경과 공백 오류 확인
git status --short
git diff --check
09 / 오해하기 쉬운 점

주의사항과 자주 묻는 질문

Unity CLI beta.17에서 달라진 설치 및 Skill 점검은?

Plugin 의존성·라이선스 및 베타 경고를 사전에 확인하고, unity skill refresh --dry-run --format json으로 프로젝트 로컬·전역 설치본의 예정된 변경과 건너뛰기·충돌을 검토합니다. 실제 Plugin/Skill 설치·갱신은 승인 후에만 수행합니다. CLI/Pipeline 자동 최신화는 기존 정책대로 유지됩니다.

ZIP을 복사하면 Unity CLI와 Pipeline이 곧바로 최신으로 업데이트되나요?

아닙니다. ZIP의 MD는 규칙 문서입니다. 실제 Unity 작업 세션에서 정해진 점검 조건이 충족될 때 해당 절차를 실행합니다. 자동 최신화는 현재 채널 및 호환성·권한·명시적 버전 고정 예외를 따릅니다.

Unity 공식 Codex Plugin, Unity Skill, Unity MCP는 같은 것인가요?

서로 다릅니다. Unity CLI 1.0.0-beta.16의 새 공식 배포 구성에서는 Plugin에 Skill이 내장되지 않으며 unity setup codex가 Plugin과 별도 Skill 설치를 구성합니다. 구형 Plugin에는 기존 Skill이 있을 수 있으므로 중복 여부를 확인합니다. MCP 연결과 프로젝트별 com.unity.pipeline 설치는 별도 절차입니다.

Unity CLI beta.16에서 Skill과 MCP는 자동 업데이트되나요?

템플릿은 Unity CLI와 현재 프로젝트의 Pipeline 자동 최신화를 유지하지만, Codex Plugin/Skill의 무조건 자동 설치·갱신까지 허용하지 않습니다. unity skill sync codex는 사용자 요청·승인을 받은 후 적용하며, unity setup all은 셸 실행이 가능한 코딩 에이전트에 MCP를 기본 등록하지 않습니다.

Editor가 막혔을 때 beta.16에서 무엇을 확인하나요?

unity pipeline editors로 로딩·Safe Mode·팝업 상태를 확인하고, 지원되는 Editor라면 unity command editor dialog로 대기 팝업을 조회합니다. 종료 코드 17은 UNAVAILABLE, 18은 AWAITING_INPUT입니다. 버튼 응답은 실제 동작을 확인한 후에만 수행합니다.

beta.16의 Unity CLI 출력 형식은 달라졌나요?

지원하는 Editor의 unity command --format json은 종전 래퍼 대신 명령 결과만 반환할 수 있습니다. TSV에는 헤더가 없으며, unity docs cache --format json 목록은 data.items에 있습니다. 기존 PowerShell·CI 파서를 점검해야 합니다.

기존 .editorconfig나 .gitignore를 덮어써도 되나요?

권장하지 않습니다. 이미 존재한다면 기존 팀 정책·Git LFS·상위 .editorconfig 등을 검토하고 필요한 설정만 병합합니다. .editorconfig의 root = true는 배포본에서 주석 처리되어 있습니다.

문서나 코드만 수정해도 자동 Push를 하나요?

프로젝트의 실제 변경 작업이라면 GIT.md의 조건에 따라 자동 Commit·Push가 수행될 수 있습니다. 다만 사용자 금지 지시, 저장소 상태, 원격 범위·보호 정책, 비밀정보 검사, 도구 권한 등 안전 조건이 우선합니다. 파일 변경 없는 분석·설명만으로 Git을 실행하지 않습니다.

기존 .cs 파일이 BOM 없는 CRLF인데 수정하면 어떻게 하나요?

그 파일의 실제 내용을 수정했다면 목표 형식인 UTF-8 with BOM + LF로 정규화합니다. 한글 손상과 Git Diff를 확인합니다. 읽기만 한 파일, Unity 자동 생성 파일, 작업 외 파일은 변환하지 않습니다.

VALIDATION.md / Batch/Validate.ps1은 왜 없나요?

READ.md와 AGENTS.md에서 선택적 Harness 검증 도구로 분류하며, 이 배포용 ZIP에는 포함하지 않았습니다. 검증 시스템이 실제 프로젝트에 설치되어 있고 관련 요청이 있을 때만 적용하도록 설계되어 있습니다.

History HTML은 Git Push 성공 여부를 계속 갱신하나요?

아닙니다. History HTML에는 작성 시점의 Git 상태를 저장하고, Commit ID와 최종 Push 결과는 Git 로그 및 최종 사용자 보고에서 관리합니다. Push 이후의 자동 HTML 재수정은 반복 커밋을 피하기 위해 제한합니다.

기존 uGUI·TMP 화면을 UI Toolkit으로 자동 교체하나요?

아닙니다. 신규 UI의 기본은 UI Toolkit이지만 기존 화면의 uGUI/TMP 구조와 참조는 유지합니다. 혼용·마이그레이션은 사용자 요청 및 실제 호환성 검증이 필요합니다.
